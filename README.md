# 遥测 UDP 代理（接收器 A/B 切换 + 同名换址自动改绑）

遥测终端经 UDP 代理把短报文发给接收器，值班员在网页上切换接收器 A/B，
已建立的会话不受影响，回包不会送错设备。

接收器重建换了 IPv4（服务名不变、DNS 已更新）时，持续上报的旧会话会自动改绑到
同名新实例：保留原会话编号，在 A 的新地址恢复原来的收发。

## 组成

| 组件 | 说明 |
|---|---|
| `proxy/` | asyncio UDP 代理 + Flask 操作网页 + SQLite 持久化 |
| `receiver/` | 本地接收器，原样回显报文，可延迟回包 |
| `docker-compose.yml` | 一键启动代理 + 接收器 A + 接收器 B |
| `scripts/verify_local.py` | 无 Docker 环境下的端到端行为验证 |
| `docker-compose.rebind-a.yml` | 演示“A 保留服务名换 IPv4、延迟就绪”的 Compose 覆盖文件 |

## 启动

```bash
docker compose up --build
```

- 操作网页：http://localhost:8080
- 遥测终端发送地址：`UDP <宿主机>:9000`

## 行为规则

- **会话**：按客户端 `IP:端口` 建立，分配递增的会话编号，空闲 5 秒
  （`SESSION_IDLE_TIMEOUT`）无收发即过期。会话编号在改绑前后保持不变。
- **建会话时固定接收器**：会话期间的一切报文都发往建会话那一刻的目标接收器；
  网页切换 A/B 只影响之后新建的会话，旧会话继续走原接收器。
  网页切到 B 后，A 的旧会话仍会保留编号并在 A 的新地址上恢复收发。
- **原样透传**：报文与回包内容不做任何修改。
- **回包不错投**：每个会话使用一条独立的、已 connect 到其当前上游 IPv4 的 UDP
  套接字（独立本地端口），只有该接收器的回包会被送回该客户端。
- **DNS 共享查询**：每个接收器名（A/B）只由一个后台解析器查询（`DNS_POLL_INTERVAL`，
  默认 2 秒），所有活动会话共用该结果；每次只采用一个 IPv4。
  DNS 结果里当前地址仍在则保持不变；否则采用 DNS 返回的第一个地址。
  **解析失败保留上一次成功地址并自动重试**。
- **同名换址自动改绑**（接收器 A 重建换了 IPv4）：
  1. 后台解析发现地址变化，为该接收器名下的活动会话启动改绑；
  2. 先建好指向候选 IPv4 的新 UDP 通道（**准备**）；
  3. 从候选 IPv4 的接收器内部就绪接口确认**同名实例就绪**，记住其实例编号；
  4. 经过稳定观察窗口（`REBIND_HOLD`）后再次确认 DNS 未再换址、且实例编号未变，
     才完成**接管**；准备与接管必须对应同一实例；
  5. 解析失败、实例未就绪、名称不匹配、确认失败、建通道失败、DNS 再换址时，
     **保留原通道照常收发**，并按退避（`REBIND_RETRY_MIN/MAX`）自动重试。
- **等待期间不中断**：解析中或确认就绪期间，原通道继续发送与接收。
- **接管后**：旧通道标记退役并保留观察期（`RETIRED_LINGER`），其上迟到的回包一律丢弃，
  不转发给客户端；已发送的报文不重发。
- **迟到结果**：改绑准备结果只在会话仍有效时生效；会话已过期/被替换时取消进行中的
  改绑并关闭新通道，**绝不会恢复过期会话**。DNS 再换址后，旧确认不能用于接管。
- **迟到回包（会话过期）**：会话过期即关闭其上游端口，端口进入冷却期
  （`UPSTREAM_PORT_COOLDOWN`，默认 30 秒，应大于最大回包延迟）不再分配；
  因此相同 `IP:端口` 重建的新会话也不可能收到旧会话迟到的回包。
- **切换可靠性**：切换先写 SQLite 再生效，保存失败保留原目标并在网页报错。
- **重启**：目标接收器保存在 SQLite（`proxy-data` 卷）重启后保留；
  会话全在内存，重启即清空。

## 接收器内部就绪接口

`receiver` 启动时先监听内部 HTTP（默认业务端口 + 1，即 `9002`），提供：

```json
GET /readyz
{"name": "A", "instance": "A-1a2b3c4d5e6f", "ready": true, "state": "ready",
 "udp_bound": true, "udp_verified": true, "udp_port": 9001, ...}
```

- `instance` 每次进程启动都重新生成，用来区分“同名接收器”的不同实例；
- UDP 端口绑定成功、并通过自检报文证明**能收业务报文**之后才报告 `ready`；
- `READY_DELAY` 可让实例绑定 UDP 成功后再延迟若干秒才报告就绪（模拟重建较慢）；
- 集成的 `${RECEIVER_A_READY_PORT}` / `${RECEIVER_B_READY_PORT}` 指向该接口；
  设为 `0` 可关闭就绪校验（不推荐）。

## 网页功能

- **切换目标接收器**：一键切换 A/B。
- **接收器状态**：每个接收器的 DNS 服务名、当前采用的上游 IPv4、DNS 代次、
  最近确认的就绪实例编号与状态、解析失败原因；地址变化时会话自动改绑。
- **发送试传报文**：可设置回包延迟（秒）、客户端端口、等待超时；
  结果显示**会话编号、实际去向接收器、实际上游 IPv4、已确认实例、回包与 RTT、
  改绑状态与改绑失败原因**。
  - 不填端口：每次试传都是新会话（走当前目标）。
  - 填同一端口（或点"用原端口重试"）：空闲 5 秒内复用**原会话**（编号不变、
    仍走原接收器）；会话过期后同端口重建新会话。
  - 接收器换址后仍用原客户端端口试传，可在 A 的新地址继续收发。
- **活动会话 / 报文日志**：实时查看每个会话的编号、固定接收器、实际上游 IPv4、
  已确认实例、改绑状态/失败原因，以及每条报文的实际去向、实例与回包
  （每 2 秒自动刷新）。

## 接收器延迟回包

- 环境变量 `REPLY_DELAY`：该接收器所有回包的默认延迟秒数。
- 报文级覆盖：报文以 `DELAY:<秒>:` 开头时按该值延迟（回包仍是完整原始报文）。

## 配置（环境变量）

| 变量 | 默认 | 说明 |
|---|---|---|
| `UDP_LISTEN_PORT` | `9000` | 代理对终端的 UDP 监听端口 |
| `HTTP_PORT` | `8080` | 操作网页端口 |
| `SESSION_IDLE_TIMEOUT` | `5` | 会话空闲超时（秒） |
| `RECEIVER_A_HOST/PORT`、`RECEIVER_B_HOST/PORT` | 见 compose | 接收器 DNS 服务名与业务端口 |
| `RECEIVER_A_READY_PORT`、`RECEIVER_B_READY_PORT` | 业务端口+1 | 接收器内部就绪接口端口；`0` 关闭校验 |
| `DNS_POLL_INTERVAL` | `2` | 每个接收器共用的后台 DNS 查询间隔（秒） |
| `DNS_TIMEOUT` | `3` | 单次 DNS 查询超时（秒） |
| `RESOLVER_HOSTS_FILE` | 空 | 可选：hosts 格式的本地 DNS 覆盖文件（每次查询重新读取） |
| `REBIND_HOLD` | `1` | 改绑接管前的稳定观察窗口（秒） |
| `REBIND_RETRY_MIN/MAX` | `1/5` | 改绑失败后的重试退避（秒） |
| `OPEN_RETRY_MIN/MAX` | `0.5/3` | 新会话解析/建通道失败后的重试退避（秒） |
| `RETIRED_LINGER` | `10` | 接管后旧通道保留观察期（秒），期间迟到回包丢弃 |
| `READY_TIMEOUT` | `1.5` | 就绪接口查询超时（秒） |
| `DB_PATH` | `/data/proxy.db` | SQLite 路径（目标持久化） |
| `UPSTREAM_PORT_MIN/MAX` | `20000/29999` | 上游本地端口池 |
| `UPSTREAM_PORT_COOLDOWN` | `30` | 上游端口关闭后的冷却秒数 |

接收器侧：`RECEIVER_NAME`、`LISTEN_PORT`、`HTTP_PORT`（就绪接口）、`BIND_HOST`、
`READY_DELAY`、`REPLY_DELAY`。

## 本机演示：A 保留服务名换 IP（Docker）

固定子网 + 本地 hosts 覆盖文件模拟“DNS 已更新”：

```bash
# 1. 启动（receiver-a=172.28.0.10，receiver-b=172.28.0.12）
docker compose -f docker-compose.yml -f docker-compose.rebind-a.yml up --build -d

# 2. 网页 http://localhost:8080 用固定客户端端口试传一次，记下会话编号与实际上游 IP
#    （应为 172.28.0.10:9001）；保持同一客户端端口继续试传 = 同一会话

# 3. 启动“重建后的 A”：receiver-a2=172.28.0.11，RECEIVER_NAME 仍为 A，
#    实例编号是新的，READY_DELAY=8 让它启动后 8 秒才报告就绪
docker compose -f docker-compose.yml -f docker-compose.rebind-a.yml up -d receiver-a2

# 4. 模拟 DNS 更新：receiver-a → 172.28.0.11
cp scripts/rebind-a/hosts-standby scripts/rebind-a/hosts

# 5. 观察网页：接收器 A 当前 IPv4 变为 172.28.0.11；改绑先显示“尚未就绪”，
#    此时原通道仍在 172.28.0.10 上正常收发、会话编号不变；
#    receiver-a2 就绪后约一个观察窗口（REBIND_HOLD）内自动完成交接，
#    实际上游 IP 变为 172.28.0.11。

# 6. 用原客户端端口再试传，确认在 A 的新地址收发正常。

# 7. 恢复演示环境：把 receiver-a 改回 172.28.0.10
printf '172.28.0.10 receiver-a\n172.28.0.12 receiver-b\n' > scripts/rebind-a/hosts
```

`scripts/rebind-a/hosts` 的初始内容即换址前状态；第 4 步覆盖后按第 7 步改回即可反复演示。

## 本地验证（无需 Docker）

```bash
pip install flask
python3 scripts/verify_local.py
```

逐项验证：原样透传（含二进制）、网页切 B 后 A 的旧会话不迁移、同名换址后旧会话
保留编号并在 A 的新 IPv4 恢复、就绪前不交接且原通道照常收发、DNS 再换址后旧确认
不能接管、接管后旧通道迟到回包丢弃且不重发、解析失败/候选不可达/名称不匹配时保留
原通道并重试、网页试传显示编号/实际 IP/回包/失败原因、迟到的改绑结果不恢复过期会话、
过期后迟到回包不投递、重启保留目标并清空会话、保存失败保留原目标。
